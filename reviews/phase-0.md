### Intended deviations from DESIGN.md and decisions the design leaves open

- **Status and enum-like columns are `text`, not Postgres enums.** The status vocabularies
  (run status, message status, tool_call status, handoff status) are owned by phases 2, 4 and 6.
  Postgres enums make every vocabulary change an `ALTER TYPE` migration; `text` keeps those
  phases free to define the vocabulary in Pydantic/Python. Check constraints can be added
  later once the vocabularies are settled.
- **`doc_chunk.embedding` is an untyped `vector` (no fixed dimension).** The design does not fix
  an embedding model; phase 5 will. An untyped `vector` column accepts any dimension but cannot
  carry an HNSW/IVFFlat index, so phase 5 must add a migration that sets the dimension and the
  index. Recorded so it is not forgotten.
- **`doc_chunk.tsv` is a stored generated column** (`to_tsvector('english', text)`) with a GIN
  index, so the tsvector can never drift from the text. English is hard-coded for now; the
  design's later multi-language question (section 21.3) will need a per-source config.
- **Primary keys are UUIDs generated by Postgres (`gen_random_uuid()`)** except `doc_source.id`
  (the human-readable source id from `sources.yaml`) and `customer_memory` (composite
  `(customer_ref, key)` as the design's table description implies).
- **Extra columns not listed in section 17:** `created_at` on `message`, `tool_call`,
  `handoff`, `doc_source`, `doc_chunk`, `kg_*`, `eval_run`; `updated_at` on `tool_call`;
  `chunk_index`, `locator`, `stale` on `doc_chunk`; `config` on `doc_source`; `attributes`
  and `source_id`/`source_version` on `kg_entity`/`kg_relation`. All are needed to implement
  the behaviour sections 9 and 15 describe and are cheaper to add now than to migrate later.
- **`run.conversation_id` is indexed but not unique.** The design's turn loop says "load Run"
  per conversation, which suggests one run per conversation, but it does not say whether a
  reopened conversation gets a new run. Phase 2 owns that decision; it can tighten the constraint.
- **mypy is `--strict` from phase 0**, not phase 1 as PLAN.md allows. The skeleton is small
  enough that starting strict costs nothing and avoids a later cleanup commit.
- **CLI uses `click`** rather than typer or argparse: subcommand groups map directly to the
  `support pack validate | knowledge sync | eval | replay` shape in section 18 and it is
  simple to test with `CliRunner`.
- **No repositories yet.** Section 18 lists "repositories" under `storage/`; phase 2 is the
  first consumer, so the module is a docstring stub only.
- **No advisory locking, no pending-message handling.** Both are phase 2 (section 7.1).
